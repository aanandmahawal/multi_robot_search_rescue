13Software architecture

The project is about 9,000 lines: a Python package rescue/ (simulation, AI and a small web server), a JavaScript 3-D front end that uses three.js, scripts for experiments, and 94 automated tests. Nothing needs a GPU; PyTorch is used on the CPU for the detector.

13.2 One step in code

Simulator.step():
    for each robot:  _sense(r)       # lidar.scan → mapping.apply_lidar; sensors.visible_cells → apply_camera;
                                     # sensors.render → detector.detect → _report (into the robot's outbox)
    _groups = groups()               # who can talk to whom (radio range, walls)
    _communicate()                   # merge maps; apply new reports in id order; registry.settle → verdicts
    _decide()                        # distance fields; special goals; coordination.choose; _route → planners.plan
    _act()                           # scans, looks, charging; conflict-free moves; energy; dead-end recovery
    _score()                         # ground-truth bookkeeping for the metrics

13.3 The dashboard: server and browser

The server is a small standard-library HTTP server (ThreadingHTTPServer). Each browser gets its own session (its own simulator), so two people can run different missions at once. The browser asks for batches of steps and draws the result:

EndpointReturns
/api/reset?building=…&robots=…a new mission with those settings; the world (walls, furniture, zones, patterns) as JSON
/api/step?n=Kadvance K seconds; the new state: robots (position, goal, route, reason, plan, battery, pattern, track), team map, searched cells, thermal map, frontiers, candidates, metrics, log
/api/camerathe selected robot's colour / thermal images and heatmap as PNG
/api/comparestarts a background job that runs the same mission once per option (planner, pattern, avoidance, strategy)
/api/victim_map, /api/revealthe exportable victim map; reveal the ground truth when the count is unknown

Large grids are sent compactly: the team map as one character per cell, the searched layer as bits, the thermal map as bytes. The front end (plain ES modules, no build step) builds the building once with instanced meshes, then each step repaints the floor texture (map, searched fog, frontiers, patterns, tracks) and moves the robots, gliding between states for smooth animation.

13.4 Tests and scripts

94 tests (pytest, about 6 minutes) check the maths and the behaviour: A* returns Dijkstra's optimal length while expanding fewer cells; the octile heuristic never overestimates; every planner returns a valid route never shorter than the optimum; Bresenham lines have octile length; RRT* tree costs stay consistent after rewiring; lanes are at most w apart; spirals go outside-in and always turn the same way; robots really drive their patterns (every reached waypoint was driven through, the median distance from the pattern is at most 0.36 m); every navigation option searches 100 % of the building; robots never drive faster than their speed; the same settings give the same mission; batteries never run flat and recharging resumes the pattern; robots sharing their reports always agree; no object ever cuts off part of a building; and the dashboard's numbers add up.

Interview tip: "how is your code structured?"

"Layered, like the robot's own architecture: world and sensors, then maps and perception, then decisions and motion, with one simulator class owning the loop. The simulation has no dependency on the UI, so the same code runs the web dashboard, the CLI, experiments and tests. All parameters live in one config dataclass, and every random choice comes from seeded generators, so any mission can be reproduced exactly."
